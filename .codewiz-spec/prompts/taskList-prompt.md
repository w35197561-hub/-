# 任务拆分阶段（前端）

## 核心目标

将技术方案拆解为可并行、可验收、可执行的任务清单。

## 交互流程

### 输出规范（强约束）
- 默认不输出完整示例代码/可运行 Demo/大段 SQL。
- 如必须举例：每步最多 1 段，≤ 10 行，仅保留关键逻辑（优先伪代码/JSON/字段表）。
- 只有用户明确要求“给代码/给示例实现”时才扩展输出。


### Step 1: 理解技术方案

**输出内容**：
- 需求项和技术方案要点总结
- 涉及的技术组件：页面、组件、状态、API、样式
- 疑问（如有）

✋ **等待用户确认**

---

### Step 2: 确定任务结构

**输出内容**：
- **Phase 划分**（建议按层次推进）：
  - Phase 1: 基础设施（路由配置、API 封装、类型定义）
  - Phase 2: 通用组件（Button、Form、Table 等可复用组件）
  - Phase 3: 页面框架（Layout、骨架屏、空状态）
  - Phase 4: 核心功能（业务组件、交互逻辑）
  - Phase 5: 样式优化（主题、响应式、动画）
  - Phase 6: 测试与优化（单测、E2E、性能优化）

- **每个 Phase 的目标和预计任务数**

✋ **等待用户确认结构**

---

### Step 3: 拆解各阶段任务（逐个 Phase 确认）

⚠️ **一次只拆解一个 Phase**

**输出内容**（针对单个 Phase）：
- **任务列表**：

| 任务编号 | 任务描述 | 涉及文件 | 可并行 | 预计工时 |
|---------|---------|---------|--------|---------|
| T1.1 | 配置路由 | routes.tsx | - | 0.5d |
| T1.2 | 封装 API 请求层 | api/request.ts | [P] | 1d |
| T1.3 | 定义 TS 类型 | types/feature.ts | [P] | 0.5d |

- **检查点**：此 Phase 完成后如何验证

**拆分原则**：
- 页面任务：一个页面 = 一个任务（或按功能拆分）
- 组件任务：一个可复用组件 = 一个任务
- API 任务：一组相关接口 = 一个任务
- 样式任务：一个模块的样式 = 一个任务
- 粒度：0.5-2 天工作量

✋ **确认本 Phase 后再继续下一个**

---

### Step 4: 确认依赖和执行顺序

**输出内容**：
- **Phase 间依赖关系**：
  ```
  Phase 1 (基础设施)
    |
  Phase 2 (通用组件) + Phase 3 (页面框架) [可并行]
    |
  Phase 4 (核心功能)
    |
  Phase 5 (样式优化) + Phase 6 (测试优化) [可并行]
  ```

- **任务级依赖**（如有复杂依赖）
- **推荐执行顺序**
- **可并行任务标识** [P]

✋ **等待用户确认**

---

### Step 5: 整合任务清单

**输出内容**：
生成完整的 `task.md` 文档，包含：
1. 任务结构（Phase 划分）
2. 详细任务列表（每个 Phase 的任务）
3. 依赖关系图
4. 执行顺序建议
5. 总预计工时

**保存路径**：`.codewiz-spec/specs/{功能名}/task.md`

---

## 任务拆分原则

- **最小化依赖**：任务之间依赖最少
- **最大化并行**：尽可能让任务可并行执行
- **独立验收**：每个任务可独立验收（组件可独立运行、页面可独立访问）
- **合理粒度**：单个任务 0.5-2 天工作量
- **分层推进**：基础设施 → 通用组件 → 业务组件

## 粒度参考

✅ **好的粒度**：
- 一个任务 = 一个页面/组件（带样式和基本交互）
- 一个任务 = 一组相关的 API 封装
- 一个任务 = 一个可独立预览的交付物

❌ **需要拆分**：
- 任务涉及多个页面、多个独立组件
- 任务跨多个功能模块

✅ **可以合并**：
- 任务只改几行代码（如修改文案、调整样式）
- 多个小改动在同一个组件内
