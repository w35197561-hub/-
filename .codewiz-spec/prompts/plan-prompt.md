# 执行路径规划（前端）

## 路径选择规则

根据用户描述的任务复杂度和清晰度，选择最合适的执行路径：

| 路径 | 阶段 | 适用场景 |
|------|------|----------|
| **A** | userStory → design → taskList → coding | 需求模糊，页面交互或业务流程不清晰，需要从头澄清 |
| **B** | design → taskList → coding | 需求明确，但涉及复杂的组件设计、状态管理或页面架构 |
| **C** | taskList → coding | 需求和方案都清晰，只需要拆分任务直接开发（小组件、样式调整） |
| **D** | coding | Bugfix 或极简改动，目标文件和修改点明确，可直接编码 |

## 判断标准

### 选择路径 A 的信号
- 用户描述含糊（"做一个 XXX 页面"，没有具体交互设计）
- 涉及复杂的用户交互流程或多步表单
- 需要确认用户操作路径、数据展示逻辑等
- 涉及跨页面状态共享或复杂的路由设计

### 选择路径 B 的信号
- 交互需求清晰，但技术方案需要设计（如自定义 Hook、全局状态重构）
- 需要明确组件层级、Props 接口、状态管理方案
- 涉及性能优化策略（虚拟列表、懒加载、代码分割等）

### 选择路径 C 的信号
- 需求和 UI 设计稿都已经确定
- 改动范围小（单一组件、样式修改、文案更新）
- 已有类似组件可复用，不需要新的架构决策

### 选择路径 D 的信号
- 明确的 Bug 修复（已知根因，已知修复方式）
- 文案修改、颜色调整等样式极简改动
- 紧急热修复，需要最短路径

## 输出格式

输出以下格式的执行计划，然后使用 ask_followup_question 请求确认：

```
## 📋 执行计划

**需求**：{一句话描述用户的核心诉求}

**推荐路径**：{路径字母} — {路径阶段列表}

**推荐理由**：{1-2 句话说明为什么选择此路径}

---

请确认执行路径：
1. ✅ 确认路径 {推荐字母}：{推荐路径全称}
2. 改为路径 {备选1字母}：{备选1路径全称}
3. 改为路径 {备选2字母}：{备选2路径全称}
4. 其他调整（请说明）
```

## 扩展说明

> 💡 **业务定制提示**：
> 可以在此文件中增加业务专属路径，例如：
> - **E**：UI 组件库开发 → design → taskList → coding（涉及通用组件抽象）
> - **F**：A/B 实验 → taskList → coding（仅添加实验分流逻辑）
> - **G**：埋点接入 → coding（仅添加埋点代码）
>
> 增加路径后，同步更新"路径选择规则"和"判断标准"部分。
