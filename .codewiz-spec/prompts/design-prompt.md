# 技术方案设计阶段（前端）

## 核心目标

将需求转化为可落地的前端技术方案，明确组件设计、状态管理、路由、样式等技术细节。

## 交互流程

### 输出规范（强约束）
- 默认不输出完整示例代码/可运行 Demo/大段 SQL。
- 如必须举例：每步最多 1 段，≤ 10 行，仅保留关键逻辑（优先伪代码/JSON/字段表）。
- 只有用户明确要求“给代码/给示例实现”时才扩展输出。


### Step 1: 理解需求与约束

**输出内容**：
- 核心功能点总结
- 技术约束：现有技术栈（React/Vue/Angular）、UI 组件库
- 性能要求：首屏加载时间、交互响应时间
- 兼容性要求：浏览器版本、移动端适配
- 疑问清单

✋ **等待用户确认**

---

### Step 2: 确定整体架构

**输出内容**：
- **页面结构图**（文字描述）：
  - 页面层级关系
  - 路由设计
  - 页面间跳转逻辑

- **技术选型**（表格形式）：

| 技术类型 | 选型 | 理由 |
|---------|------|------|
| 框架 | React 18 | xxx |
| 状态管理 | Redux/Zustand/Context | xxx |
| 路由 | React Router v6 | xxx |
| UI 组件库 | Ant Design/Material-UI | xxx |
| CSS 方案 | CSS Modules/Styled Components | xxx |
| 构建工具 | Vite/Webpack | xxx |

- **组件层级**：
  ```
  App
  |-- Layout (布局)
  |   |-- Header
  |   |-- Sidebar
  |   +-- Content
  |       +-- FeaturePage (功能页面)
  |           |-- FeatureList (列表组件)
  |           +-- FeatureForm (表单组件)
  ```

- **需要讨论的决策点**：客户端渲染 vs SSR、状态管理方案等

✋ **等待用户确认整体架构**

---

### Step 3: 细化技术细节（逐个模块确认）

⚠️ **一次只讨论一个技术组件**

#### 3.1 组件设计

**输出内容**：
- **组件拆分**（每个功能页面）：
  - 容器组件（页面级）：负责数据获取、状态管理
  - 展示组件（UI 组件）：负责渲染、交互
  - 通用组件（可复用）：Button、Form、Table 等

- **组件接口设计**（Props）：
  ```typescript
  interface FeatureListProps {
    data: DataItem[]
    loading: boolean
    onEdit: (id: string) => void
    onDelete: (id: string) => void
  }
  ```

- **组件状态**（State）：哪些状态需要在组件内部管理

**提问方向**：
- 是否需要组件懒加载？
- 是否需要虚拟滚动？
- 是否需要考虑组件缓存？

✋ **确认后继续下一个**

---

#### 3.2 状态管理设计

**输出内容**：
- **全局状态**：
  - 用户信息、权限、主题配置
  - Store 结构设计

- **页面状态**：
  - 列表数据、筛选条件、分页信息
  - 表单数据、校验状态

- **状态更新逻辑**：
  - Action/Reducer 设计（Redux）
  - 或 Hooks 设计（Zustand/Context）

**提问方向**：
- 哪些状态需要持久化（LocalStorage）？
- 是否需要状态回溯/撤销？

✋ **确认后继续下一个**

---

#### 3.3 API 调用设计

**输出内容**：
- **API 层封装**：
  ```typescript
  // api/feature.ts
  export const fetchFeatureList = (params: QueryParams) => {
    return request.get('/api/features', { params })
  }
  ```

- **数据处理**：
  - 请求拦截器（token、请求头）
  - 响应拦截器（错误处理、数据转换）
  - 重试机制

- **加载状态管理**：
  - Loading、Error、Empty 状态
  - 骨架屏设计

**提问方向**：
- 接口是否需要防抖/节流？
- 是否需要请求取消？

✋ **确认后继续下一个**

---

#### 3.4 样式设计

**输出内容**：
- **CSS 架构**：
  - 全局样式（reset、theme）
  - 组件样式（模块化、作用域）

- **主题配置**：
  - 颜色变量、字体、间距
  - 深色模式支持

- **响应式设计**：
  - 断点设计（mobile、tablet、desktop）
  - Flex/Grid 布局

**提问方向**：
- 是否需要支持国际化？
- 是否需要支持 RTL 布局？

✋ **确认后继续下一个**

---

### Step 4: 确认代码改动位置

**输出内容**：
- **新增文件**：
  - 页面文件：pages/FeaturePage.tsx
  - 组件文件：components/FeatureList.tsx
  - API 文件：api/feature.ts
  - 样式文件：styles/feature.module.css

- **修改文件**：哪些现有文件需要改动（路由配置、全局状态等）
- **功能入口**：从哪个菜单/路由进入
- **影响范围**：会影响哪些现有页面

✋ **等待用户确认**

---

### Step 5: 确认上线保障

**输出内容**：
- **功能开关**：如何控制新功能开启
- **灰度策略**：按用户/百分比灰度
- **性能优化**：
  - 代码分割（Code Splitting）
  - 懒加载（Lazy Loading）
  - 资源压缩（Gzip、Brotli）
- **监控告警**：关键指标（页面加载时间、错误率）

✋ **等待用户确认**

---

### Step 6: 整合文档

**输出内容**：
生成完整的 `design.md` 文档，包含：
1. 架构设计（页面结构、技术选型）
2. 组件设计
3. 状态管理设计
4. API 调用设计
5. 样式设计
6. 代码改动位置
7. 上线保障

**保存路径**：`.codewiz-spec/specs/{功能名}/design.md`

---

## 关键原则

- **组件化思维**：合理拆分组件，提高复用性
- **状态清晰**：明确状态的归属和流转
- **性能优先**：考虑加载速度、渲染性能
- **可维护性**：代码结构清晰，易于扩展
- **用户体验**：交互流畅，反馈及时
